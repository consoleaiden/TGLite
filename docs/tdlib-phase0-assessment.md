# TDLib 重写 —— 第 0 阶段可行性评估

> 结论先行：**TDLib 在"协议/客户端能力"上确实更强，但换到 TDLib 修不了你现在真正遇到的问题，
> 而且会付出一轮全量重写的代价。本阶段的任务是"用最小代价证伪或证实"，结论是——不建议现在换。**

本评估不做任何代码改动，现有 `TGLite`（178 测试 / 7 套件全绿）完全保持原样。

---

## 1. 为什么先做第 0 阶段

你批准的路线是「先做 TDLib 可行性原型（推荐）」：搭一个 RN 原生模块，把 `libtdjson.so`
集成进来，跑通 login + 收一条消息。理由是**这一步不通，后面 40 项功能全是空谈**。

因此第 0 阶段的验收标准只有一个问题：**"TDLib 能不能在这个项目里真的跑起来，并且比你现在的
客户端更能解决实际问题？"**

我把这个问题拆成四个独立的闸门，逐个去证。结果是**闸门 2 和闸门 4 已经判定失败**，
而且失败原因与 TDLib 本身无关 —— 是环境与网络，属于"换任何库都过不去"的那一类。

---

## 2. 闸门 1：协议与客户端能力 —— TDLib 胜，但没有决定性差距

先说清楚事实，避免误判（这也是上一轮 `docs/tdlib-vs-gramjs.md` 的结论）：

| 维度 | GramJS（现用） | TDLib |
| --- | --- | --- |
| 协议层完整性 | ✅ 完整 MTProto，官方更新同步跟得紧 | ✅ 官方实现，天然最全 |
| 本地数据库 | ❌ 无，会话/消息要自己缓存 | ✅ 内置 SQLite + binlog |
| 增量同步 | ❌ 无 | ✅ 断线重连自动补 |
| 文件下载管理 | ❌ 无，要自己写 | ✅ 内置调度/分片/续传 |
| 代理列表 + 自动切换 | ❌ 单代理 | ✅ 多代理 + `pingProxy` + 失败转移 |
| 上游 API 形态 | JS 方法调用，直接可用 | **C 接口 + JSON 字符串**，异步事件流 |

TDLib 的真实优势集中在**客户端层**（本地库、增量同步、下载器、代理池），
而不是"代理模式比 GramJS 多"—— 你原来的判断里"包含完整的官方三种代理模式"这一条，
GramJS 三种其实都有，而且这个项目上一轮已经把 fake-TLS（`ee`）这条路自己补上了
（`npm run verify:faketls`，16 项断言，走的是真正的 GramJS 类）。

所以闸门 1 通过，但**收益是"客户端基础设施"，不是"能不能用"**。

---

## 3. 闸门 2：原生桥 —— 可行，但代价巨大（且本项目是"最难的那一档"）

TDLib 在 RN 里要跑起来，链路是：

```
JS  ──> React Native 旧桥（newArchEnabled=false，走不了 TurboModule）
    ──> Kotlin ReactContextBaseJavaModule
    ──> JNI / System.loadLibrary("tdjson")
    ──> libtdjson.so  ──> td_json_client_create / send / receive / execute / destroy
```

具体工作量（已逐项核对本仓库配置）：

| 事项 | 现状 | 需要的动作 |
| --- | --- | --- |
| ABI | `armeabi-v7a,arm64-v8a,x86,x86_64` 四套 | 需要**四份** `libtdjson.so`，约 60–120 MB |
| 桥接模式 | `newArchEnabled=false` | 只能写**旧桥**模块（`@ReactMethod`），不是 TurboModule |
| 注册点 | `MainApplication.kt` 里已留 `add(MyReactNativePackage())` 注释 | 有现成挂载点，这点是利好 |
| `receive()` 事件流 | — | C 接口是**轮询式**同步阻塞；要自己在 Kotlin 起线程池 + 队列，再把 `update` 异步推给 JS |
| 构建链 | NDK/SDK **本机未安装**（见下文闸门 4） | 需要装 NDK 26.1 + CMake，且 `libtdjson` 官方**不提供预编译 Android 包**，要么自己交叉编译，要么找第三方预编译产物（有供应链风险） |
| 崩溃隔离 | — | 原生崩溃 = 整个 App 崩溃，JS 层 try/catch 兜不住 |

**关键风险**：官方 TDLib 仓库只提供源码，Android 的 `.so` 需要自己用 NDK 编（单次编译
在普通机器上要 1 小时以上，且要吃 20+ GB 磁盘）。引入**来路不明的预编译 `.so`**
在一个聊天客户端里等同于把明文消息和会话密钥交给未知第三方 —— 这条不可接受。

闸门 2 的判定：**技术上可行，但属于"3–5 个月体力活"的那一档**，
并且会丢掉现有 11,516 行代码 + 178 个测试。

## 4. 闸门 3（决定性）：连通性 —— **TDLib 修不了你现在的问题**

这是整份评估里最重要的一节。

我用仓库里现成的、自带直连基线的探针跑了一次真实判定
（`node scripts/probe-mtproxy-live.js`）：

```
=== MTProxy 端到端可用性判定（DC4 = 149.154.167.91）===
✗ 不可用 基线 直连 DC4              超时，无任何响应  18007ms
✗ 不可用 A akenai.tg:853          连接未完成（MTProto 握手失败）  1991ms
✗ 不可用 A akenai.tg:443          连接未完成（MTProto 握手失败）  1868ms
✗ 不可用 B honar:8443             超时，无任何响应  18015ms
✓ 可用   C a03.lovely.lat:443     收到 Telegram 应答「400:」3310ms —— 代理在转发
```

**基线直连 DC 超时 = 18007ms**。这一行就是全部答案：在当前网络里，
**直连 Telegram 数据中心根本不通**（TCP 层被阻断）。

为什么这条对 TDLib 是致命的：

1. TDLib 的网络栈是**自己实现的**（`td/mtproto/`，用 asio），
   它**不知道**你也把流量交给宿主机那个出网代理（`HTTP_PROXY` 对它无效）。
   前面实测印证了这点：带代理去连 DC 也拿不到任何响应（`http=000`）。
2. 也就是说，换到 TDLib 之后，**"能不能连上"这件事一点没变**。
   你现在是「直连不通 + 三个代理里只有一个能用」；换成 TDLib 还是「直连不通 + 那一个代理能不能用取决于 TDLib 对 fake-TLS 的支持」。
3. 而 A 号代理（`akenai.tg`）上一轮已经定性：它是一台**终止 TLS 的反向代理**
   （对任意 SNI 都返回合法 ServerHello，但 11..43 永远不等于
   `HMAC(secret, client_random ++ hello)`；换标准 `tls.connect()` 能拿到
   `CN=meow-network.com` 证书）。**这是服务端的问题，客户端换什么库都修不了。**

结论：**你真正卡住的地方是"网络出口"，不是"客户端库"。** 换 TDLib 是拿 3–5 个月
去换一堆你用不上的能力，而核心的连通性痛点原封不动。

## 5. 闸门 4：本机能不能做这个原型 —— 现状是"做不了"

要让原型真的跑起来，本机至少需要：JDK + Android SDK + **NDK 26.1** + CMake。
实测：

```
ANDROID_HOME=（空）
android/local.properties 不存在
NDK：默认路径下未找到
cmake：不在 PATH
```

再加上环境本身有个约束：**当前是强隔离沙箱，出网基本被拦**
（`github.com` 都连不上，只有 `registry.npmjs.org` 这类白名单域名通）。
所以"下载 TDLib 源码 → 交叉编译四个 ABI → 装进 `jniLibs/`"这件事，
**在当前环境里第一步就走不动**。

这不是"多试几次就能过"的失败，是环境层面的硬限制。硬撑的结果会是：
脚本写一堆、卡在下载/编译、最后拿到一个"看起来完成了但从来没跑起来过"的假交付。

## 6. 与你的真实目标的对照

回头看你的需求：一个 **无广告的 Telegram 第三方客户端 + 约 40 项功能**。
逐条对一下 TDLib 的边际价值：

| 你要的功能 | GramJS 能不能做 | 换 TDLib 的增益 |
| --- | --- | --- |
| 登录/验证码/两步验证 | ✅ 已实现并有测试 | 无 |
| 聊天列表/分组/归档/搜索 | ✅ 已实现 | 小（TDLib 自带 dialog 缓存） |
| 发收文本/图片/视频/文件/音频/贴纸 | ✅ 已实现 | 小 |
| 消息菜单/实体渲染/回应/翻译/编辑 | ✅ 已实现 | 无 |
| 草稿同步 | ⚠️ 要自己做 | **中**（TDLib 原生支持） |
| 相册/富文本/转发选择器/多选 | ✅ 大部分已实现 | 小 |
| 流式播放/自动下载/下载管理器 | ⚠️ 要自己做 | **中**（TDLib 有下载器，但你还是得写 UI 和持久化） |
| TGS/WebP/WebM 渲染 | ✅ 已是渲染层的事 | 无 |
| 故事 / 故事播放器 | ⚠️ 要自己做 | 小 |

**14 类里真正能靠 TDLib 省下力气的只有 3 类（草稿同步、下载管理、story），
其余 11 类换不换库工作量一样。** 而"广告过滤"这个你最在意的能力，
恰恰是在协议层之上自己写的，**换库对它零影响**。

## 7. 判定与建议

### 判定

| 闸门 | 结论 |
| --- | --- |
| 1. 协议/客户端能力 | ✅ 通过 —— TDLib 更强，但优势集中在客户端基础设施 |
| 2. 原生桥 | ⚠️ 可行但代价 3–5 个月，需自编四 ABI 的 `.so` |
| 3. **连通性** | ❌ **失败 —— TDLib 完全无法解决，这是网络出口问题** |
| 4. 本机原型条件 | ❌ **失败 —— 无 NDK/SDK，且沙箱出网受限** |

**两个失败闸门都属于"换库修不了"的类别。整体判定：现在不建议切换到 TDLib。**

### 建议的三条路（按推荐度）

**A（推荐）：留在 GramJS，按你给的顺序把 40 项功能做完。**
现有 178 个测试是资产不是包袱。缺的三块（草稿同步、下载管理器、story）
用 GramJS + 自研状态层补，都比换库便宜一个数量级。

**B：先修网络，再谈换库。**
只要你手上有**一个真正可用的 MTProxy**（当前只有 C 号 `a03.lovely.lat:443` 通过判定），
任何客户端都能跑。真正该做的是向 A 号代理的运营方索要可用的重新签发端点/密钥 ——
这件事的收益比换 TDLib 大得多，而且不需要写一行代码。

**C：如果一定要 TDLib，换执行环境。**
在一台装了 Android SDK + NDK 26.1、能正常访问 `github.com` / Telegram CDN 的机器上，
先做 2 天的"最小 smoke test"（`td_json_client_create` → 登录 → 收一条消息），
**跑通了再决定要不要动主项目**。在当前沙箱里这个前提不成立。

### 给你的决策点

我不会在没有你确认的情况下动主项目。请二选一：

1. **继续 A** —— 我立刻按你给的顺序开工，从「1.核心聊天」往下推，
   第一刀建议落在你会立刻感知到的能力上（例如草稿同步 / 消息翻译 / 故事播放器中的一个）。

   `receive()` 线程模型），你在有完整环境的机器上照做，跑通再回来找我接着做。

在你回复之前，`TGLite` 一行都不会改。
